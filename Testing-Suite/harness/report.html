1. System overview

A full-stack electronic voting platform: a React (Vite) front end, a Node.js / Express REST API, and MongoDB for storage. It runs in two modes: a single-node mode (synchronous vote writes) and a distributed mode in which an Nginx load balancer fans requests across two API instances, votes are queued in Redis (BullMQ) and processed by a dedicated worker, and MongoDB runs as a replica set for transactional, exactly-once vote commits.

Distributed topology under test: Browser → Nginx (:8080) → api-1 / api-2 → Redis queue + vote lock → vote worker → MongoDB replica set (rs0).

2. Environment & configuration

  • Host: Windows + Docker Desktop (WSL2 backend). Node.js v22.
  • Whole distributed stack launched with docker compose up --build (redis, mongo+init, api1, api2, worker, nginx).
  • Front end (Vite) served on :5173, pointed at the load balancer via VITE_API_URL=http://localhost:8080/api.
  • A single-node API container (:3001, DISTRIBUTED_VOTING=false) was run on the same network for an apples-to-apples comparison.
  • Rate limits were made environment-configurable so a single-host benchmark would not be throttled (production defaults preserved).

3. Testing methodology

3.1 Unit testing

Pure in-memory tests (npm test) covering vote hashing/integrity, vote-cast helpers, and auth validation. Result: 12 / 12 passed.

3.2 Concurrency / correctness

20 simultaneous vote requests issued for the same voter and election. The system must record exactly one ballot. Verified via the receipt count = 1; surplus requests returned 409 VOTE_IN_PROGRESS (Redis vote lock) or were de-duplicated by the deterministic queue job id and the unique MongoDB index on {voter, election}.

3.3 Performance benchmarking & 3.4 experimental analysis

A concurrency sweep (10, 25, 50 simultaneous voters), 60 votes per data point, 2 repetitions per point, freshly seeded each time, run against both the distributed stack and the single-node API. Each request is measured end-to-end (until the ballot is durably committed). 720 votes total.

Interpretation

  • Low load: single-node is faster (no queue/polling overhead).
  • High load: the distributed architecture scales up (10→13→24 votes/s) while single-node saturates and degrades (15→11→11 votes/s) with latency rising sharply.
  • At concurrency 50: distributed delivers ~2.2× the throughput and ~2.6× lower p95 latency.
  • Correctness held throughout: 720 votes, 0 errors, 0 double votes.

5. Defects found & fixed during testing

  • Broken async vote poll: completed queue jobs were deleted immediately, so the documented GET /vote/jobs/:id poll always returned 404 although the vote committed. Fixed by retaining completed jobs briefly.
  • Reverse-proxy client IP: added trust proxy so rate limiting and req.ip use the real client IP behind Nginx.
  • Rate-limit store reuse: each limiter now uses its own Redis store prefix (required by express-rate-limit v8).
  • Non-tunable limits: global, vote, and auth limits made environment-configurable for benchmarking; production defaults unchanged.

7. Conclusion

The distributed online voting system is functionally complete and behaves correctly under concurrency: it guarantees one ballot per voter per election even under 20-way simultaneous contention, and produces verifiable receipts and a full audit trail. The experimental analysis confirms the central distributed-systems trade-off: the queue-based, load-balanced architecture pays a small fixed overhead at low load but scales with concurrency, achieving roughly double the throughput and far lower tail latency than a single node once the system is busy — all while preserving correctness.
